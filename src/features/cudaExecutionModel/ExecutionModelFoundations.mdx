<Section
id="frame"
title="Mental model"
note="This is the execution-model layer: first make the logical work correct, then ask what the SMs, warps, and resources are doing."
>

CUDA is easiest to learn when you stop treating `<<<grid, block>>>` as decoration and start
treating it as a contract. The launch creates a logical grid of thread blocks. Each thread
computes an index. The hardware then places blocks onto streaming multiprocessors, forms
warps, and issues ready warp instructions while respecting resource limits.

What the host chooses

The host code chooses the grid shape, the block shape, optional dynamic shared memory, and
the stream. Those choices define how many logical threads exist and how much block-local
state each block needs.

What the hardware chooses

The GPU decides when each block becomes resident on an SM and which ready warp issues next.
The launch does not guarantee block order, SM assignment, or that a larger block will run
faster.

What the kernel must prove

The kernel must map each thread to valid data, guard extra threads, and keep cross-block
assumptions out of ordinary launches. Correct indexing is the first invariant. Performance
comes after that invariant is observable.

<Callout title="One sentence to keep nearby" tone="success">
Start with <code>block = 256</code> and <code>grid = ceil(problem_size / block)</code>,
prove the index and guard, then tune with block-size sweeps, occupancy evidence, and profiler
metrics.
</Callout>
</Section>

<Section
id="syntax"
title="Launch syntax"
note="Most beginner code only needs the first two launch parameters. The third and fourth matter when dynamic shared memory or streams enter the design."
>

A CUDA kernel launch puts an execution configuration between the kernel name and its
arguments. The first value is the number of blocks in the grid. The second value is the
number of threads in each block. The optional third value is dynamic shared memory bytes per
block. The optional fourth value is the stream.

<CodeBlock language="cuda" title="Launch syntax">{`kernel<<<gridDim, blockDim, dynamicSharedMemoryBytes, stream>>>(args...);

vecAddKernel<<<ceil(n / 256.0), 256>>>(A_d, B_d, C_d, n);

// Equivalent launch intent:
gridDim  = ceil(n / 256.0); // number of blocks
blockDim = 256;             // threads per block`}</CodeBlock>

The syntax is compact, but it hides four separate questions:

how many threads are available inside each block.

<Section
id="coverage"
title="Indexing and coverage"
note="The last block often contains extra threads. That is normal; the bounds guard makes the launch work for arbitrary sizes."
>

For a simple vector kernel, each thread owns one output element. The host launches at least
`n` logical threads. The kernel computes a global index and checks whether that index names a
real element before touching memory.

<CodeBlock language="cuda" showLineNumbers title="vec_add.cu">{`__global__ void vecAddKernel(const float* A,
                             const float* B,
                             float* C,
                             int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        C[i] = A[i] + B[i];
    }
}

int block = 256;
int grid  = (n + block - 1) / block;
vecAddKernel<<<grid, block>>>(A_d, B_d, C_d, n);`}</CodeBlock>

The useful accounting line is:

<CodeBlock language="text" title="Coverage ledger" wrap>{`useful elements   = n
blocks launched   = (n + block - 1) / block
threads launched  = blocks launched * block
guard threads     = threads launched - n`}</CodeBlock>

For `n = 1003` and `block = 256`, CUDA launches 4 blocks and 1024 logical threads. The final
21 threads are not a bug. They are the price of using a simple rectangular launch shape for a
non-rectangular input size.

<Callout title="Correctness invariant" tone="success">
Every memory access should be justified by an index formula and a bounds guard. Keep at least
one non-divisible input size in the test set so the final-block path is exercised.
</Callout>
</Section>

      <tr>

The practical order is: first prove the grid covers the data, then prove each thread's index
is valid, then inspect warp behavior and SM resource fit. A launch that is logically correct
can still be slow, but a launch with broken ownership accounting is not ready for profiling.
</Section>

<Section
id="sms"
title="Blocks are not SMs"
note="Only persistent kernels and some work-queue designs usually tie grid size intentionally to SM count."
>

A common beginner mistake is launching one block per streaming multiprocessor. Ordinary
data-parallel kernels usually launch many more blocks than the GPU has SMs. The scheduler
places blocks onto SMs in waves, and different thread blocks do not have a guaranteed order.

<div className="cuda-command-table-wrap">
  <table className="cuda-command-table">
    <thead>
      <tr>
        <th scope="col">Pattern</th>
        <th scope="col">Launch habit</th>
        <th scope="col">Why</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <th scope="row">Normal data-parallel kernel</th>
        <td>Launch enough blocks to cover the data, often far more blocks than SMs.</td>
        <td>More independent blocks give the scheduler work to distribute and reduce tail effects.</td>
      </tr>
      <tr>
        <th scope="row">Persistent kernel</th>
        <td>Sometimes launch <code>SM_count * k</code> blocks and let each block pull from a queue.</td>
        <td>The blocks are deliberately long-lived workers instead of one block per data tile.</td>
      </tr>
    </tbody>
  </table>
</div>

The rule is not "ignore SM count." The rule is to use it for the right question. SM count is
useful when limiting a grid-stride loop, sizing persistent workers, or interpreting profiler
occupancy. It is not the default number of blocks for a vector add.
</Section>

<Section
id="warps"
title="Warp lens"
note="NVIDIA hardware executes threads in warps. Current compute-capability tables still list a warp size of 32, while other resource limits vary by architecture."
>

CUDA exposes threads, but performance often becomes visible at warp granularity. A 256-thread
block contributes 8 warps. A 128-thread block contributes 4 warps. A 1024-thread block
contributes 32 warps and can leave fewer block-level scheduling choices on an SM.

<CodeBlock language="cuda" title="Baseline launch shapes">{`// First CUDA baseline for a 1D data-parallel kernel:
int block = 256;
int grid  = (n + block - 1) / block;
kernel<<<grid, block>>>(...);

// First CUDA baseline for row-major 2D data:
dim3 block(16, 16); // 256 threads
dim3 grid((width  + block.x - 1) / block.x,
          (height + block.y - 1) / block.y);
kernel2D<<<grid, block>>>(...);`}</CodeBlock>

The useful warp questions are:

1. Are adjacent `threadIdx.x` lanes accessing adjacent memory addresses?
2. Does the branch condition give the same answer for every lane in a warp?
3. Does the block size create a whole number of warps?
4. Do registers and shared memory still allow enough resident warps to hide waits?

<Callout title="Why 256 survives as a baseline" tone="success">
256 threads per block is 8 warps. That is usually enough warps to help hide latency while
leaving room for more than one block per SM when registers and shared memory allow it.
</Callout>
</Section>
