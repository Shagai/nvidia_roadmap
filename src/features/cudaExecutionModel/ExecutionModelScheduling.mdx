<Section
id="scheduling"
title="Warp scheduling"
note="The scheduler hides waits by switching to ready resident warps. It does not make a slow memory operation faster."
>

An SM does not schedule one arbitrary CUDA thread at a time. It keeps blocks resident, tracks
their warps, and issues instructions from warps whose next instruction is ready. When one
warp reaches a long wait, such as a global-memory load, the scheduler can issue work from a
different resident warp.

That is the core latency-tolerance model: a slow operation is still slow, but the SM may have
other useful warp instructions to issue while that operation is pending.

<CodeBlock>{`// Hardware-level mental model, not literal scheduler order:
cycle 0: issue Warp 0 instruction
         Warp 0 loads from global memory and stalls

cycle 1: issue Warp 1 instruction
cycle 2: issue Warp 2 instruction
cycle 3: issue Warp 3 instruction

later:   Warp 0's memory data is ready
         Warp 0 becomes eligible to issue again`}</CodeBlock>

<Section
id="divergence"
title="Divergence"
note="Divergence is a warp-level question. Inspect one warp's lanes, not only the source line."
>

A branch diverges when lanes in the same warp need different instruction paths. CUDA does not
make that branch wrong, but it can make the warp run paths serially with different active
lane masks. Loops follow the same rule: if the exit condition varies by lane, some lanes stop
participating while the warp continues for lanes that still have work.

<CodeBlock>{`// Diverges in the first warp: lanes 0, 1, and 2 disagree with lanes 3..31.
if (threadIdx.x > 2) {
    do_taken_path();
} else {
    do_other_path();
}

// Common boundary guard. Usually only the final partial warp diverges.
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) {
    C[i] = A[i] + B[i];
}

// Loop divergence: each lane can have a different trip count.
int limit = a[threadIdx.x];
for (int k = 0; k < limit; ++k) {
    do_work(k);
}`}</CodeBlock>

<Callout title="Boundary divergence is often the right tradeoff" tone="success">
For vector addition with <code>n = 1003</code> and <code>block = 256</code>, the launch
creates 1024 logical threads. The final block has 235 useful threads and 21 guard threads,
so only the last warp in that block is partially active. That small amount of divergence is
usually better than special-case launch code for every input length.
</Callout>

<Section
id="occupancy"
title="Occupancy and resource fit"
note="This figure is a teaching model. For exact values, use the real kernel's registers, shared memory, target architecture, and CUDA occupancy APIs."
>

Occupancy is the resident-warps view of a launch. A block must fit on one SM before it can
run. Resident blocks are limited by threads, warps, registers, shared memory, resident-block
slots, and architecture-specific limits. If no block fits, the launch fails. If only one
block fits, the SM may have too few independent warps to hide latency.

<CodeBlock>{`activeBlocksPerSM = min(
    maxBlocksPerSM,
    maxThreadsPerSM / threadsPerBlock,
    maxWarpsPerSM / warpsPerBlock,
    registerLimit,
    sharedMemoryLimit,
    otherHardwareLimits
);

activeWarpsPerSM = activeBlocksPerSM * warpsPerBlock;
occupancy        = activeWarpsPerSM / maxWarpsPerSM;`}</CodeBlock>

<Callout title="Why 1024 is not automatically better" tone="warning">
A 1024-thread block contains 32 warps. On an SM profile with a 1536 resident-thread limit,
the thread limit alone allows only one such block per SM. With 256-thread blocks, the same
thread limit can allow six blocks and 48 resident warps before other resources are counted.
