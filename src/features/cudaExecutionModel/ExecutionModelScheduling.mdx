<Section
id="scheduling"
title="Warp scheduling"
note="The scheduler hides waits by switching to ready resident warps. It does not make a slow memory operation faster."
>

An SM does not schedule one arbitrary CUDA thread at a time. It keeps blocks resident, tracks
their warps, and issues instructions from warps whose next instruction is ready. When one
warp reaches a long wait, such as a global-memory load, the scheduler can issue work from a
different resident warp.

That is the core latency-tolerance model: a slow operation is still slow, but the SM may have
other useful warp instructions to issue while that operation is pending.

<CodeBlock>{`// Hardware-level mental model, not literal scheduler order:
cycle 0: issue Warp 0 instruction
         Warp 0 loads from global memory and stalls

cycle 1: issue Warp 1 instruction
cycle 2: issue Warp 2 instruction
cycle 3: issue Warp 3 instruction

later:   Warp 0's memory data is ready
         Warp 0 becomes eligible to issue again`}</CodeBlock>

<Section
id="memory-latency"
title="Hiding global-memory latency"
note="Latency hiding means overlapping waits with other useful work. It does not make a single global-memory access cheap."
>

Global memory can be slow for one warp and still deliver high throughput for the whole GPU.
The difference is overlap. CUDA hides global-memory latency at the SM level by switching to
other ready resident warps, and the memory system hides DRAM latency by spreading requests
across channels and banks so one request can be preparing while another transfers.

The practical lesson is that latency hiding needs both enough independent warp work and a
memory access pattern that lets the memory system combine and distribute traffic.

<h3>Two places where overlap happens</h3>

<div className="cuda-command-table-wrap">
  <table className="cuda-command-table">
    <thead>
      <tr>
        <th scope="col">Layer</th>
        <th scope="col">What waits</th>
        <th scope="col">What hides the wait</th>
        <th scope="col">What breaks it</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <th scope="row">SM warp scheduler</th>
        <td>A warp issues a global load and cannot issue its dependent instruction yet.</td>
        <td>Other resident warps are eligible, so the scheduler issues their instructions.</td>
        <td>Too few resident warps, too many dependent loads, barriers, divergence, or long dependency chains.</td>
      </tr>
      <tr>
        <th scope="row">DRAM channels</th>
        <td>One channel is busy with a burst transfer.</td>
        <td>Other channels have separate buses and can transfer different memory transactions.</td>
        <td>Traffic concentrates on too few channels or arrives as small scattered transactions.</td>
      </tr>
      <tr>
        <th scope="row">DRAM banks</th>
        <td>One bank is doing the long internal activate/read work.</td>
        <td>Other banks prepare in parallel, then take turns using the channel bus for bursts.</td>
        <td>Many requests target the same bank at the same time, creating bank conflicts.</td>
      </tr>
    </tbody>
  </table>
</div>

Channels and banks answer different questions. A channel is an independent path between the
memory system and the GPU. A bank is an independent DRAM storage unit behind a channel.
More channels raise possible bandwidth. More banks help keep each channel busy by staggering
the long internal waits.

<h3 id="coalescing">Why coalescing belongs in the same explanation</h3>

Modern GPUs map consecutive memory regions across transactions, channels, and banks in ways
designed to make regular access patterns productive. When adjacent lanes read adjacent
addresses, the hardware can form fewer, wider memory transactions. Those transactions are
much easier to distribute across the memory system than scattered single-lane requests.

<CodeBlock>{`// Good: neighboring lanes read neighboring addresses.
int i = blockIdx.x * blockDim.x + threadIdx.x;
float x = A[i];

// Bad: neighboring lanes jump around memory.
int j = index_table[blockIdx.x * blockDim.x + threadIdx.x];
float x = A[j];`}</CodeBlock>

<div className="cuda-command-table-wrap">
  <table className="cuda-command-table">
    <thead>
      <tr>
        <th scope="col">Pattern</th>
        <th scope="col">What the GPU can do</th>
        <th scope="col">Performance meaning</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <th scope="row">Many active warps</th>
        <td>Issue another ready warp while one warp waits on memory.</td>
        <td>This is why occupancy and eligible-warps metrics matter.</td>
      </tr>
      <tr>
        <th scope="row">Coalesced lane access</th>
        <td>Combine adjacent lane requests into efficient memory transactions.</td>
        <td>This uses bandwidth better than many scattered requests.</td>
      </tr>
      <tr>
        <th scope="row">Distributed channel/bank traffic</th>
        <td>Overlap DRAM preparation and burst transfers across the memory system.</td>
        <td>This keeps the memory bus busier while individual accesses remain high-latency.</td>
      </tr>
    </tbody>
  </table>
</div>

For tiled matrix multiplication, this is why the simple access pattern matters before any
advanced tuning. Many blocks load tiles at the same time. If the loads are regular and
coalesced, the memory system can group them into useful transactions and distribute those
transactions across available channels and banks. Shared memory then helps by reusing the
loaded tile so the kernel asks global memory for fewer total bytes.

<Callout title="Best and worst cases" tone="success">
Best case: many active warps, coalesced accesses, and well-distributed channel/bank traffic.
Worst case: few eligible warps, scattered accesses, and requests concentrated on the same
memory resources. The first case hides much of the wait. The second case leaves SMs stalled
and memory bandwidth underused.
</Callout>

<Callout title="Profiler reading rule" tone="warning">
Do not read high occupancy as proof that memory latency is solved. Read achieved occupancy
beside eligible-warps, memory throughput, coalescing or transaction metrics, cache behavior,
and the dominant warp stall reason.
</Callout>

<Section
id="divergence"
title="Divergence"
note="Divergence is a warp-level question. Inspect one warp's lanes, not only the source line."
>

A branch diverges when lanes in the same warp need different instruction paths. CUDA does not
make that branch wrong, but it can make the warp run paths serially with different active
lane masks. Loops follow the same rule: if the exit condition varies by lane, some lanes stop
participating while the warp continues for lanes that still have work.

<CodeBlock>{`// Diverges in the first warp: lanes 0, 1, and 2 disagree with lanes 3..31.
if (threadIdx.x > 2) {
    do_taken_path();
} else {
    do_other_path();
}

// Common boundary guard. Usually only the final partial warp diverges.
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) {
    C[i] = A[i] + B[i];
}

// Loop divergence: each lane can have a different trip count.
int limit = a[threadIdx.x];
for (int k = 0; k < limit; ++k) {
    do_work(k);
}`}</CodeBlock>

<Callout title="Boundary divergence is often the right tradeoff" tone="success">
For vector addition with <code>n = 1003</code> and <code>block = 256</code>, the launch
creates 1024 logical threads. The final block has 235 useful threads and 21 guard threads,
so only the last warp in that block is partially active. That small amount of divergence is
usually better than special-case launch code for every input length.
</Callout>

<Section
id="occupancy"
title="Occupancy and resource fit"
note="This figure is a teaching model. For exact values, use the real kernel's registers, shared memory, target architecture, and CUDA occupancy APIs."
>

Occupancy is the resident-warps view of a launch. A block must fit on one SM before it can
run. Resident blocks are limited by threads, warps, registers, shared memory, resident-block
slots, and architecture-specific limits. If no block fits, the launch fails. If only one
block fits, the SM may have too few independent warps to hide latency.

<CodeBlock>{`activeBlocksPerSM = min(
    maxBlocksPerSM,
    maxThreadsPerSM / threadsPerBlock,
    maxWarpsPerSM / warpsPerBlock,
    registerLimit,
    sharedMemoryLimit,
    otherHardwareLimits
);

activeWarpsPerSM = activeBlocksPerSM * warpsPerBlock;
occupancy        = activeWarpsPerSM / maxWarpsPerSM;`}</CodeBlock>

<Callout title="Why 1024 is not automatically better" tone="warning">
A 1024-thread block contains 32 warps. On an SM profile with a 1536 resident-thread limit,
the thread limit alone allows only one such block per SM. With 256-thread blocks, the same
thread limit can allow six blocks and 48 resident warps before other resources are counted.
